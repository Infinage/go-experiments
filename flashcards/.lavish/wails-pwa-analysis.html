PWA first… or straight to a Wails3 APK?

Reading goal: you asked (a) what it takes to make this app work as a PWA and (b) whether an intermediate PWA would hinder the end goal — an APK via Wails3. Sources: the two Wails3 docs pages you saved to ~/Downloads, this repo's code. Claims marked [VERIFY] still need a on-device check.

One-sentence answer: skip the PWA. The only PWA work that carries over to Wails is a thrown-away hour (manifest + icons); the work that makes a PWA genuinely useful for this app — an offline, browser-side data layer — is a multi-day rewrite that becomes dead code under Wails, and its absence is exactly why an installed PWA on your daily-reset server buys you nothing today. The Wails port itself is small because this app is already shaped right: a plain net/http server whose frontend is static files + datastar.

The three pieces of "PWA support", and where each ends up

The crux is the pink row: SQLite cannot "work as a PWA" by itself. Our data lives in the Go process — a browser install just caches the shell while the data stays on your server. Making it offline means either SQLite-in-browser (sql.js + OPFS) or a full IndexedDB store + sync: days of work that (per the diagram) is discarded the moment Wails gives you a real SQLite file on device.

Wails3 Android: what the docs actually say

Architecture (from the Android guide)

Android WebView renders the frontend; assets are served in-process via WebViewAssetLoader — no localhost server, no open ports. Go is compiled to a C shared lib libwails.so (GOOS=android + NDK) loaded by a small Java host. "You do not need to change your Go code. The same main.go builds for all targets." (first-mobile-app page)

Toolchain (one-time)

ANDROID_HOME / ANDROID_SDK_ROOT; SDK incl. platform-tools, platforms;android-35, build-tools;35.0.0, NDK 26.3.11579264, JDK 21 (sudo apt install openjdk-21-jdk), wails3 doctor to verify. You already have commandlinetools-linux-15859902_latest.zip in ~/Downloads.

Commands you'll actually run

wails3 task android:run — build + emulator
wails3 task android:run:device — sideload to my phone (DEVICE_ID)
wails3 task android:package:fat — universal APK for quick shares
android:bundle:fat — AAB, only needed for Play

First build 5–10 min, incremental <1 min. WebView inspectable at chrome://inspect.

The port work on this repo (file by file)

  1. Entry point split. main.go:22-42 currently does http.ListenAndServe. Under Wails3 the asset/root handler is handed to the Wails app instead. Fork per platform via build tags: //go:build android calls the wails runtime with the existing internal/web handler as its AssetServer; //go:build !android keeps ListenAndServe untouched on desktop/web. [VERIFY] exact handler-API name when scaffolding.
  2. DB path. main.go:23 uses a CWD-relative flashcards.db. CWD is not writable on Android — the db must live in the app sandbox files dir. [VERIFY] preferred accessor (Wails path API vs os.UserCacheDir()).
  3. SQLite driver (modernc.org/sqlite). This answers your "sqlite3 database stuff as it is?" question: yes, genuinely — the driver is pure Go (no cgo), compiles into libwails.so unchanged, and runs the same file-based SQLite. Schema and queries don't change. Only the path from (2) moves.
  4. Biggest runtime risk — datastar SSE through the in-process asset scheme. Fragments/fetch already go over plain HTTP in-process; [VERIFY] that EventSource (SSE) is not buffered by WebViewAssetLoader on Android WebView. Fallback = datastar fetch/poll, which needs no SSE. prove-or-fallback first with a hello-world fragment.
  5. Everything else carries as-is. internal/store, templates, tailwind, camera/record JS (mobile camera already routes through the WebView's <input type=file capture> — same semantics [VERIFY]). Add 44px tap targets + safe-area insets only when the phone feels cramped.
  6. No PWA artifacts anywhere. Wails has its own launcher; a manifest/SW would be inert.

Suggested order of work

  1. Install toolchain from the zip in ~/Downloads → wails3 doctor all-green
  2. Hello-world Wails3 mobile probe first — minimal main.go + one datastar fragment over SSE through the in-process asset scheme → decide SSE vs fetch/poll (risk item 4). Don't lean on wails3 init: we already have an existing repo, so init output is a reference, not a scaffold.
  3. Replicate what wails3 init generates into the flashcards repo — study the generated Taskfile android targets, build/, app config, and port only those pieces rather than scaffolding fresh. [VERIFY] exact generated file set (v3 alpha).
  4. Port flashcards: entry split + db path, nothing else → android:run, debug via chrome://inspect
  5. android:run:device → sideload APK on your phone for real demos
  6. Later/optional for Play: android:bundle:fat + own keystore, bump versionCode per upload

Effort: toolchain 30–60 min; scratch hello-world 30–45 min; real port ≈ half a day, dominated by the SSE risk item and first-build NDK friction. Mobile support in Wails v3 is explicitly experimental — trust wails3 doctor + the build result over doc assurances.
